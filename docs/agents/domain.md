# Доменная документация

Как скилы читают доменную документацию этого репозитория, когда изучают код.

## Раскладка: single-context

Один набор на весь репозиторий (признаков монорепозитория нет):

```
/
├── GLOSSARY.md          ← словарь терминов проекта
├── docs/adr/            ← ADR: короткие записи архитектурных решений
│   └── 0001-<решение>.md
└── plugins/ctx, plugins/handoff
```

## Перед изучением кода прочитай

- **`GLOSSARY.md`** в корне репозитория.
- **`docs/adr/`** — ADR, которые касаются области, где предстоит работать.

Если этих файлов нет — **продолжай молча**. Не отмечай их отсутствие и не предлагай завести заранее:
скил `/domain-modeling` (через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их по ходу,
когда термины или решения действительно определились. Пишутся на русском.

## Пользуйся словарём глоссария

Когда в результате работы называется доменное понятие (заголовок тикета, предложение рефакторинга,
гипотеза, имя теста), используй термин так, как он определён в `GLOSSARY.md`. Не уходи в синонимы,
которые глоссарий явно отвергает.

Если нужного понятия в глоссарии нет — это сигнал: либо ты придумываешь язык, которым проект не
пользуется (пересмотри), либо это настоящий пробел (отметь для `/domain-modeling`).

## Отмечай конфликты с ADR

Если результат противоречит существующему ADR, скажи об этом явно, а не перекрывай молча:

> _Противоречит ADR-0007 (…), но стоит пересмотреть, потому что…_
